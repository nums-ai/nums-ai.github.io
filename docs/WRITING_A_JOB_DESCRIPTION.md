# Write a job description

Every position on the Careers page comes from one Markdown file in
`src/content/careers/`, including Open Application. Files are discovered
automatically; no imports, registry, or React edits are needed.

## Add or upload a role

1. Copy `src/content/careers/_template.md` to a new file in that same folder,
   such as `research-engineer.md`. You can also create or upload the file in GitHub.
2. Set its title, order, and status in the YAML frontmatter between the `---` lines.
3. Write the description below the frontmatter using ordinary Markdown.
4. Set `status: open` when it is ready to appear on the site.
5. Commit the file and merge it into `main`. The existing GitHub Pages workflow
   builds and publishes both `/careers/` and `/careers/en/`.

```markdown
---
title: "Research Engineer"
order: 30
status: open
---

Help turn research ideas into reliable model training systems.

## What you’ll do

- Build reproducible experiments and evaluate new model ideas.

## What we’re looking for

- Experience with Python and deep learning frameworks.

## Nice to have

- Experience training tabular foundation models.
```

This is an example, not an approved opening. Replace the title and description
with the actual JD before publishing.

## Fields and filenames

| Item | Purpose |
| --- | --- |
| Filename | A lowercase, hyphen-separated name ending in `.md`. It also becomes the role's anchor, e.g. `/careers/en/#research-engineer`. Keep it stable when changing the title. |
| `title` | The title shown in the position header and page outline. Quote it, especially if it includes a colon. |
| `order` | A nonnegative integer; lower numbers appear first. Equal values are ordered by filename. Existing roles use 10 and 20; Open Application uses 100. |
| `status` | `open` appears on the page. `draft` and `closed` are omitted from both the page and outline, including during local preview. |

Only `.md` files directly inside `src/content/careers/` are loaded. Files starting
with `_`, including `_template.md`, are ignored. Do not use `main`, `about`,
`conditions`, `application`, `open-positions`, `careers-outline-title`, or
`careers-positions-label` as filenames; these anchors belong to the page.

The build checks every loaded file for a valid title, order, status, and nonempty
description. Invalid metadata stops the build with the filename in the error.
Draft and closed files must keep valid metadata and a description too.

## Formatting and shared content

Use paragraphs, `##` section headings, `###` subheadings, bullet or numbered lists,
links, **bold**, and *italics*. Tables and blockquotes are supported too. The title
comes from frontmatter, so do not repeat it as a `#` heading. The site renders
`##` sections below the position heading in the accessible heading hierarchy.
Raw HTML and JSX are not rendered.

The section names and number of sections are flexible. Open Application uses
the same format without required responsibilities or qualifications sections.

Company information, working conditions, and application instructions are shared
across roles in `src/app/careers/content.en.ts`. Edit those once instead of copying
them into every JD. Presentation lives in `src/app/careers/JobDescription.tsx`
and `careers.module.css`.

## Preview, close, and publish

Run `npm run dev`, visit `/careers/en/`, and refresh the page after editing or
adding Markdown files. To review a draft locally, temporarily set its status
to `open`, then return it to `draft` before committing if it is not ready.

Before publishing, run `npm run typecheck` and `npm run build`, and check the
position's contents on desktop and mobile. `npm start` serves the most recent
build; rebuild to see content changes there. The standalone HTML generated by
`npm run share` includes the same positions.

To close a role, change its status to `closed` and publish again. Removing the file
also removes the role. If no positions are open, the page shows a short empty
state while retaining company information and application instructions.

Content changes go live after the deployment from `main` succeeds. There is no
public upload form or CMS; GitHub is the editing/upload workflow. Draft and closed
files are still visible in this public repository, so keep confidential notes out
of them.
